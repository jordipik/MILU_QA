# MILU — Auditoría Técnica Completa (Mayo 2026)

---

## FASE 1 — ANÁLISIS GLOBAL

### ¿Qué hace el proyecto?

MILU es una **herramienta interna de control de calidad para catálogos de piezas de motores** (series MTU 4000). Su función principal es gestionar el ciclo de revisión QA de artículos extraídos de PDFs de libros de recambios, comparando datos PDF vs. datos GESA vs. datos finales, y tomando decisiones de importación a WordPress.

### Inventario de vistas

| Página | Módulo JS principal | Propósito |
|---|---|---|
| `qa_milu.html` | `js/qa-milu.js` | Vista QA principal (tabla + PDF viewer) |
| `analista_02.html` | `js/analista-02.js` | Revisión campo a campo con comparación PDF |
| `pn_review.html` | `js/pn-review.js` | Vista agrupada por número de pieza |
| `qa_lista_agrupada.html` | inline | Lista agrupada por PN (alternativa a pn_review) |
| `exportacion.html` | `js/exportacion.js` | Gestión de exportación a WordPress |
| `qa_auditoria.html` | `js/qa-auditoria.js` | Visor de log de auditoría |
| `qa_analista_registro.html` | `js/qa-analista-registro.js` | Vista de registro individual (flujo registro a registro) |
| `milu_shell.html` | inline | Shell contenedor que carga vistas en iframe |

### Stack

- **Backend**: Express 5 + Node.js, CommonJS (`server.js`)
- **Frontend**: ES Modules nativos (sin bundler), HTML5, CSS custom
- **Persistencia**: 9 archivos `engine_*.json` + `qa_revision_server_data.json` + `qa_audit_log.json`
- **Dependencias externas en browser**: PDF.js 3.11, pako 2.1, Google Fonts (Manrope)
- **Python scripts**: utilidades offline de transformación (no forman parte del runtime)

### Lo que está bien estructurado

- Separación limpia de responsabilidades en `js/`: `state.js`, `helpers.js`, `qa-checks.js`, `revision.js`, `revision-sync.js` tienen responsabilidades claras y están bien encapsulados.
- Escritura atómica de JSON (tmp → rename) en `server.js` — `writeJsonAtomic()` evita corrupción.
- Sistema de caché con fingerprint de archivos en `server.js` (`pnReviewQaCache`) para el endpoint `/pn-review/list`.
- El `change-control.js` es un módulo independiente bien diseñado (undo/redo + audit).
- Whitelist explícita de archivos permitidos (`ENGINE_JSON_FILES`) en todos los endpoints de escritura.
- `safeFileName()` y `safeFolderName()` con validación path traversal en los endpoints de export.
- El sistema de revisión tiene manejo robusto de claves legacy + ID + occurrence.

### Lo que está incompleto o inconsistente

- `server.js` es un monolito de ~1.700 líneas que mezcla lógica de negocio, transformación de datos y routing sin separación alguna.
- Hay **dos archivos `pn_review`** en `js/`: `pn_review.js` y `pn-review.js`, ambos con IIFE, propósito solapado poco claro.
- La lista `ENGINE_JSON_FILES` está duplicada en 4 lugares distintos.
- `exportacion.js`, `pn-review.js` y `qa-auditoria.js` no son ES modules (usan IIFE) mientras el resto de `js/` sí lo son.
- `qa_lista_agrupada.html` tiene lógica JavaScript incrustada inline (~400 líneas) duplicando lo que ya hace `data-loader.js`.

## FASE 2 — DETECCIÓN DE PROBLEMAS

### P1. `ENGINE_JSON_FILES` definida 4 veces (alta severidad)

```
engine_files.js          ← source of truth del backend (CommonJS)
js/data-loader.js        ← frontend ES module
generate_synthetic_exports.js ← script offline
qa_lista_agrupada.html   ← inline en HTML
```

Cualquier adición de un motor nuevo requiere actualizar manualmente los 4 sitios. El frontend ya importa correctamente desde `data-loader.js`; `qa_lista_agrupada.html` debería hacer lo mismo.

### P2. `escapeHtml` duplicada en 4 módulos (media severidad)

`helpers.js` exporta `escapeHtml()` pero los siguientes módulos definen su propia copia local ignorando la import disponible:

- `js/exportacion.js` línea 42
- `js/qa-auditoria.js` (standalone)
- `js/qa-analista-registro.js` línea 35
- `js/pn-review.js` (standalone)

### P3. Lógica de negocio duplicada entre `server.js` y `scripts/`

En `server.js` se definen literalmente (no como imports) las siguientes funciones que también existen en la capa frontend/scripts:

- `normalizeText`, `collapseSpaces`, `lowerKey`, `pnKey`, `uniq`, `pickMostFrequent` — duplicadas de `helpers.js` / `export_wordpress_milu.js`
- `buildMergedFields`, `buildPnValidation`, `buildMappedSourceRow`, `buildSustSummary`, `buildConflictSummary` — lógica de construcción de payload del endpoint `/pn-review/list` (~200 líneas) que podría estar en un módulo CommonJS compartido

### P4. `decisionMap` / `explicitMap` copiado verbatim en 2 handlers

`POST /pn-review/:sku/apply-decision` y `POST /pn-review/by-id/:id/apply-decision` copian el mismo bloque:

```js
const decisionMap = { validar: {...}, descartar: {...}, revisar: {...} };
const explicitMap = { 'ok|importar': 'validar', ... };
```

Si se cambia la lógica de un handler y no del otro, el comportamiento diverge silenciosamente.

### P5. Inconsistencia de patrones de módulo en `js/`

| Archivo | Patrón |
|---|---|
| `qa-milu.js`, `qa-table.js`, `revision.js`... | ES Module (import/export) |
| `exportacion.js` | IIFE — no importa de `state.js` ni de `helpers.js` |
| `pn-review.js` | IIFE — tiene su propio `const state = {}` local |
| `qa-auditoria.js` | Función de módulo — sin exports, ejecuta al cargar |
| `qa-analista-registro.js` | ES Module pero redefine helpers localmente |

Esto hace que `exportacion.js` y `pn-review.js` no puedan compartir ni reutilizar nada del ecosistema de módulos existente.

### P6. Naming inconsistente

**Archivos:**
- `pn_review.js` vs `pn-review.js` (ambos existen)
- `pn_review.css` vs `pn-review.css` (ambos existen en `styles/`)
- `analista_02.html` / `analista_02.css` vs `pn-review.html` / `qa-milu.html`

**Campos de datos:**
- `PART NO.`, `DESIGNATION`, `QTY` — UPPER CASE con espacios (legado PDF)
- `pn_final`, `designation_final` — snake_case
- `qa_revision_estado`, `qa_revision_accion` — snake_case con prefijo
- `sourceFile`, `changeId` en change-control — camelCase

No existe ninguna convención documentada ni consistente. Los fallbacks en `COLUMN_FALLBACKS` de `helpers.js` son el síntoma: se necesitan múltiples alias por campo porque el mismo concepto tiene 4 nombres distintos.

### P7. `bulk-revision-helper.js` — lógica de búsqueda de fila frágil

```js
const selectedRow = state.allData.find(row => {
    const pn = String(row?.['PART NO.'] ?? row?.pn ?? '').trim();
    const id = String(row?.ID ?? '').trim();
    return selectedKey.includes(pn) || selectedKey.includes(id);
});
```

Usa `String.includes()` sobre la clave de revisión para buscar la fila — puede dar falsos positivos si el ID de una fila es substring del ID de otra.

### P8. `qa_lista_agrupada.html` — ~400 líneas de JS inline

Duplica la lógica de carga de `data-loader.js` con su propia copia inline de `ENGINE_JSON_FILES`. Es la única vista sin refactorizar a módulos externos.

### P9. No hay test suite

El `package.json` no tiene script `test`. No hay tests unitarios, de integración ni end-to-end. La validación de cambios se hace exclusivamente de forma manual.

### P10. `backendStatusTimer` declarado dos veces

En `qa-milu.js` (línea top) y en `topbar.js` existe un `backendStatusTimer` local propio. El `qa-milu.js` también tiene su propio timer independiente. Coexisten dos timers de polling del backend en la misma página, uno del topbar y otro del módulo principal.

## FASE 3 — UX / UI

### Consistencia entre páginas

| Aspecto | Estado |
|---|---|
| Topbar compartido | `topbar.js` funciona bien para `qa_milu.html`, `analista_02.html` y `qa_lista_agrupada.html`. Las vistas `exportacion.html`, `pn_review.html` y `qa_auditoria.html` tienen su propio header ad-hoc |
| Backend status badge | Implementado en topbar, pero `exportacion.html` tiene un badge propio `#expBackendStatus` con lógica diferente |
| Estilos | `qa_milu.html` carga 3 hojas CSS distintas (`pdf_shared.css`, `qa_milu.css`, `analista_02.css`). El acoplamiento CSS entre páginas es opaco |
| Fuente | Manrope desde Google Fonts en todas las páginas, pero la fuente está declarada en cada HTML individualmente |

### Puntos de fricción identificados

**Botones bulk action opaco (alta friccción)**
```html
<button id="bulkRevOkBtn" ...>V</button>
<button id="bulkRevEmptyBtn" ...>P</button>
<button id="bulkValidateBtn" ...>I</button>
<button id="bulkReviewBtn" ...>R</button>
<button id="bulkDiscardBtn" ...>X</button>
```
Las etiquetas son `V`, `P`, `I`, `R`, `X` — solo descifrables con el `title` en hover. No hay texto visible. Para operaciones masivas irreversibles, esto es una fuente de error.

**Ausencia de confirmación en acciones bulk destructivas**
Las acciones masivas (`bulkDiscardBtn`, `bulkRevEmptyBtn`) no tienen diálogo de confirmación. Un clic erróneo en "X" sobre "Todos los filtrados" puede marcar como eliminar cientos de filas simultáneamente.

**`milu_shell.html` como iframe container no documentado**
El shell carga páginas en iframe y permite navegación entre vistas, pero varias páginas también pueden abrirse directamente (standalone). El comportamiento en modo embedded vs standalone no está claramente diferenciado en la UI.

**Feedback de guardado**
`cell-editor.js` aplica `cell-saving` class pero la recuperación de errores muestra `alert()` nativo. Las otras páginas usan `appendLog()` (exportacion) o llamadas a `alert()` directas. No hay un sistema unificado de notificaciones/toasts.

**Paginación de tabla**
La tabla tiene paginación con número de página y botones anterior/siguiente, pero los filtros de book/page están separados de los filtros de columna, generando dos jerarquías de filtrado visualmente desconectadas.

### Lo que funciona bien en UX

- El split-view tabla/PDF en `qa_milu.html` con redimensionado drag es una solución efectiva para el flujo de trabajo.
- El panel de esquemas (pos circles) integrado da contexto visual inmediato.
- Los filtros de columna con debounce son rápidos y no bloquean la UI.
- El indicador de estado del backend en el topbar da visibilidad clara sobre la conectividad.
- Los shortcuts de teclado (`Ctrl+Z` para undo, flechas para navegar filas) están documentados en tooltips.

## FASE 4 — PROPUESTA DE MEJORA

### 4.1 Extraer lógica de negocio de `server.js` a módulos CommonJS

El 60% del código de `server.js` es lógica de transformación de datos que no tiene nada que ver con el routing HTTP.

**Estructura propuesta:**

```
server/
  routes/
    pn-review.js       ← endpoints /pn-review/*
    export.js          ← endpoints /export/*
    revision-sync.js   ← endpoints /qa_revision_sync.php
    audit-log.js       ← endpoints /audit-log
    save-json.js       ← endpoints /save-json
  services/
    pn-review-cache.js ← ensurePnReviewQaDataLoaded + cache
    row-transforms.js  ← buildMergedFields, buildPnValidation, etc.
  utils/
    normalize.js       ← normalizeText, collapseSpaces, lowerKey, uniq
server.js              ← solo bootstrap y use() de routers
```

### 4.2 Crear fuente única de verdad para `ENGINE_JSON_FILES`

`engine_files.js` ya existe como fuente CommonJS. El frontend `data-loader.js` ya tiene su propia lista (correcta). La solución más simple es documentar que ambas listas deben mantenerse sincronizadas, o mejor, generar un `engine_files.json` que ambos lean en runtime.

### 4.3 Convertir `exportacion.js` y `pn-review.js` a ES modules

Para poder importar `escapeHtml`, `state`, `fetchJsonSafe` y demás desde el ecosistema compartido. Esto elimina 3 duplicaciones directas y habilita la reutilización futura.

### 4.4 Estandarizar el patrón de módulos frontend

Todos los archivos en `js/` deberían ser ES modules con `export`. Los que actualmente son IIFE (`exportacion.js`, `pn-review.js`, `qa-auditoria.js`) deben migrarse o al menos documentarse como excepción.

### 4.5 Extraer `decisionMap` a constante compartida en `server.js`

```js
// Al nivel de módulo, una vez
const DECISION_MAP = {
    validar: { estado: 'ok', accion: 'importar' },
    descartar: { estado: 'ok', accion: 'eliminar' },
    revisar: { estado: 'pendiente', accion: 'revisar' }
};
const EXPLICIT_MAP = {
    'ok|importar': 'validar',
    'ok|eliminar': 'descartar',
    'pendiente|revisar': 'revisar'
};
```

Y una función `resolveDecision(action, estadoRaw, accionRaw)` que ambos handlers llamen.

### 4.6 Reemplazar botones bulk con etiquetas legibles + confirmación

```html
<!-- Propuesta -->
<button id="bulkRevOkBtn" class="quick-action-btn validate">✓ OK</button>
<button id="bulkDiscardBtn" class="quick-action-btn discard">✕ Eliminar</button>
```

Con confirmación modal para las acciones destructivas (eliminar, vaciar) cuando el scope afecte más de N filas.

### 4.7 Sistema de notificaciones unificado

Reemplazar `alert()` nativo y los `appendLog()` ad-hoc con un toast system centralizado:

```js
// js/notifications.js
export function showToast(message, level = 'info', duration = 3000) { ... }
export function showError(message) { ... }
```

### 4.8 Estructura de carpetas ideal

```
milu/
  server.js            ← bootstrap ligero
  engine_files.js      ← fuente única ENGINE_JSON_FILES (CommonJS)
  server/              ← lógica backend separada
  js/                  ← todos ES modules
  styles/              ← unificar nombres a kebab-case
  docs/                ← documentación (ya existe, bien organizada)
  scripts/             ← utilidades Node.js offline
  data/                ← outputs generados
  *.html               ← vistas
```

## Resumen ejecutivo

El proyecto MILU tiene una **arquitectura funcional y razonablemente sólida** para una herramienta interna de uso local. Los módulos de frontend están bien separados por responsabilidad, la persistencia JSON es simple y el backend implementa protecciones correctas (whitelist de archivos, escritura atómica, validación de inputs).

Las tres deudas técnicas más urgentes son:

1. **`server.js` monolítico** — 1.700 líneas con lógica de negocio mezclada con routing. Si crece, se vuelve inmantenible.
2. **`ENGINE_JSON_FILES` en 4 sitios** — cada nuevo motor requiere editar 4 archivos distintos, con riesgo de inconsistencia.
3. **Botones bulk sin etiqueta** — `V`, `I`, `R`, `X` son un vector de error operativo en acciones masivas irreversibles.
